# Languages and internationalization

The repository separates documentation translations, the home-tools answer
language, native Assist sentences, speech recognition, speech synthesis and
wake-word models. A translated README does not install a voice or prove that
speech recognition works in that language.

## What the integration supports

Version `0.3.0` of `echomuse_home` selects its response-language instruction from
the language Home Assistant supplies in each conversation's `LLMContext`:

- `en`: English.
- `ru`: Russian.
- `de`: German.
- `es`: Spanish.
- `fr`: French.

The language is selected for each API instance. Different Assist pipelines can
therefore use the same local Ollama home-tools API in different languages.
Model quality still depends on the selected local model; this is an instruction
to that model, not a guarantee that every answer will obey it.

Common tags normalize to their base language, such as `en-US`, `en_GB`, `ru-RU`,
`de-Latn-DE`, `es-419` and `fr-CA`. Case and surrounding whitespace are ignored.
Missing, malformed and unsupported values use **Russian**, preserving the
existing installation's default. Locale strings never become prompt text:
only the five fixed catalog instructions can be selected. Private-use extensions
and encoding suffixes such as `.UTF-8` are intentionally unsupported.

The local-only-agent error has Home Assistant exception translation metadata and
catalogs in all five languages. HA can use that metadata when displaying the
error; client paths that display raw exception text retain its English fallback.
This is independent of the conversation response language. The component is configured through YAML; it
does not invent a configuration flow or translate an upstream EchoMuse UI.
Low-level tool errors, field names, operation names, entity IDs and domain names
remain stable machine-facing values. The model should explain tool errors in
the response language without claiming that the failed action succeeded.

Native `EchoMuseGetState` sentence and response files are supplied for **English
and Russian**. They cover current sensor values, on/off questions and lists of
lights. They are read-only and use HA's target matching, Assist exposure and user
permission checks. Historical questions stay on the Recorder-backed tool path;
a current sensor counter is not consumption over a requested period. German,
Spanish and French do not have project-specific native sentence files yet; their
model route requires suitable entity names or aliases.

The search policy includes common Russian-to-English name normalization. Other
languages require matching aliases; it is not a general machine translator.
For example, assign `Küchenlampe`, `lámpara de cocina` or `lampe de cuisine` to the
correct light rather than expecting those words to resolve an English name by
themselves. Put aliases in this integration's `aliases` configuration for the
tool path and in HA's entity/area settings for native Assist matching. These are
separate catalogs; neither changes control permissions.

## Configure another language

1. Keep the working pipeline as a rollback option. Follow
   [Home control](home-control.md) to install the complete component directory,
   including its `translations` directory, and to select its API in the local
   Ollama agent. Updating only `__init__.py` is insufficient.
2. For native English state questions, copy
   `examples/custom_sentences/en/echomuse_home.yaml` into
   `custom_sentences/en/echomuse_home.yaml` under HA's configuration directory.
   Keep the Russian file under `custom_sentences/ru/` if needed. Preserve other
   custom sentence files. Validate configuration and restart HA after installing
   or updating the component and sentence files.
3. In **Settings → Voice assistants**, create or edit a pipeline and choose its
   language. Select an STT service and a TTS voice that both support that
   language. A Russian Piper voice does not acquire English, German, Spanish or
   French pronunciation from this setting.
4. Use the language-neutral instructions from
   [the agent prompt example](../examples/home-assistant-prompt.txt). Remove
   conflicting fixed-language instructions from the agent's existing prompt;
   the home-tools API now chooses the answer language. Keep all permission,
   ambiguity and action-verification instructions.
5. Assign the pipeline to the intended satellite's Assistant selector(s).
   Neither flashing the Dot nor a USB connection is required for this change.
6. Test in Assist's text interface first with real exposed names. For English,
   try `What is the first heater power?`, `Is the first heater on?` and
   `Which lights are on?`. For Russian, try «Какова мощность первого
   обогревателя?», «Включён ли первый обогреватель?» and
   «Какие лампы включены?». Compare readings to HA, then perform an attended
   speaker test using the same phrases. The example names must exist as aliases
   in your own installation.

The wake word is a separate acoustic model: changing the pipeline language does
not translate it. Both pilot Dots now use the privately trained **«Привет, Мышка»**
model instead of Hey Jarvis. This is a deployed trial whose independent
room-distance acceptance is still pending; see its
[training and deployment record](russian-wake-word.md). Other phrases require
their own training and false-activation testing; see the
[Russian voice roadmap](russian-voice-roadmap.md).

## Permissions and privacy are independent of language

Every language uses the same tools, control allowlist, bounded arguments,
per-user permission checks, eight-action limit and ambiguity handling. Locale
selection cannot enable another provider or broaden device access. A cloud
provider still cannot obtain this API just by requesting `ru` or `en`.

The platform gate accepts the Ollama integration. Its configured endpoint must
actually be local; the platform name alone cannot establish network privacy.
Keep the workload isolation described in [Home control](home-control.md).
Using a cloud STT provider still sends microphone audio outside the home,
regardless of where the model and TTS run. There is no automatic cloud fallback
for unsupported languages in this component.

## Validation and present limits

The dependency-free checks cover all five catalog entries, normalization,
Russian fallback, malformed locale/instruction input and exception-translation
completeness:

```sh
python3 -m unittest discover -s tests -p 'test_home_*.py' -v
```

The isolated Home Assistant runtime checks actual `probatio` tool schemas,
unchanged API routing and authorization, per-conversation language selection,
English/Russian sentence matching and HA-rendered response templates. Native
questions remain read-only; control commands, negations and history questions
are excluded from the sample current-state grammar:

```sh
docker run --rm --network none --entrypoint python3 \
  -v "$PWD:/work:ro" -w /work \
  ghcr.io/home-assistant/home-assistant:2026.10.0@sha256:1b64d38f38d922bf9d59336451fd6453e1d614f934456af4ee3d2a51061be3a4 \
  -m unittest discover -s tests -p 'runtime_home_tools.py' -v
```

These tests use synthetic HA entities and mock services, not home devices.
They do not measure model fluency, recognition accuracy, a voice's pronunciation
or wake-word reliability. The existing deployment has attended Russian speaker
checks. English native templates have software validation; German, Spanish and
French currently have bounded prompt-language selection and translated provider
errors, not equivalent end-to-end speaker validation.

For a new language, add a fixed catalog entry, the corresponding exception
translation, locale tests, and native sentence/response files only when they have
recognition and template tests. Keep machine tool names unchanged. Document the
chosen STT/TTS providers and attended results separately from README coverage.
